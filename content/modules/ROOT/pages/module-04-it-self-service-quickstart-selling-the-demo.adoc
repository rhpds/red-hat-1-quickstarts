== The ACME Story

Lead with the story, not the architecture. It gives the customer a mirror to see themselves in.

Every enterprise runs the same tax on its people. An employee needs a new laptop, so they go hunting: which policy applies, am I even eligible yet, what can I order in my region, who approves it, and where do I file the ticket? Half the requests that reach IT are wrong — missing information, the wrong model, outside policy — so they bounce back, and the clock starts over.

The IT Self-Service Agent collapses all of that into one conversation. The employee just says what they want. The agent checks eligibility against policy, shows the options that are actually available to them, confirms the choice, and opens the ServiceNow ticket for them. The request lands correct the first time.

For your customer, the pitch is simple. This isn't a smarter help desk form. It's an agent that *completes the request* — applying the rules automatically so fewer requests get rejected, more close faster, and IT gets its time back.

== How It Works

You don't need to teach the architecture to sell it, but one picture earns credibility when the technical buyer in the room asks "what's actually happening?" A request manager takes the incoming message off whatever channel it arrived on. A routing agent reads intent and hands off to the right specialist. The specialist pulls grounded context — policy and catalog — from knowledge bases and tools, and when it's time to act, it calls a system like ServiceNow through an MCP server to create the ticket.

== Exercise 1: Run the Laptop-Refresh Demo

// VERIFY against the live environment before the event: confirm the Webmail tab, the pre-seeded users, and the laptop-refresh flow behave as written.
This is the heart of the demo. You'll play an employee emailing IT and let the agent walk the whole request to a filed ticket. Everything happens inside Showroom — you click the *Webmail* tab and you're in.

A word on the channel, because a customer will ask. The agent "meets employees where they already work" — their email. What you're looking at here is a test inbox standing in for a real corporate mailbox, so you can drive the conversation live. That's a strength, not a workaround: no new app for employees to learn, no portal to adopt. They email IT the way they already do, and an agent answers.

[TIP]
====
Pre-warm the model before you start narrating. As soon as you open the *Webmail* tab, send the first "Hello" email *before* you turn to the customer. The first response spins the model up and can be slower; get that out of the way off-camera so the first reply the customer sees comes back fast. LLM responses can take 10–30 seconds — when you're live, treat that pause as talk-time and narrate the value while the agent works.
====

. In the right pane, click the *Webmail* tab to open the test inbox.
. Select the user *alice.johnson@company.com*. The subject is pre-filled with *Laptop refresh*.
. Send a simple opener. In the message body, type this and send:
+
[source,text]
----
Hello
----

. The routing agent greets Alice. Narrate it: "She didn't fill out a form or pick a category. She said hello, and the system is already figuring out who should help."
. Now state the request. Type this and send:
+
[source,text]
----
I'd like to start a laptop refresh request
----

. The routing agent hands off to the laptop specialist, which comes back with Alice's laptop information and eligibility, and offers to show options. This is the first selling beat: say "It already knows who Alice is, what she's on today, and whether she's eligible — before she's typed a single detail."
. Ask to see what she can order. Type this and send:
+
[source,text]
----
I'd like to see available laptop options
----

. The agent lists four laptop options with specs and pricing *for Alice's region*. Point out that these aren't a generic list — they're the models actually available to her under policy.
. Make a choice. Short answers work. Type this and send:
+
[source,text]
----
option 1
----

. The agent confirms the selection and asks for approval. Narrate the compliance angle: "It's confirming before it acts — no request gets filed half-complete or out of policy."
. Approve it. Type this and send:
+
[source,text]
----
Yes, please create the ticket
----

. The agent creates the ticket and returns a ticket number, for example *REQ3143724*. This is the close of the demo: a real request, resolved end to end, with a tracking number the employee can hold onto.

====
To run the flow again from the top — for a different persona or a second take — just send an email containing `reset`.

== Exercise 2 (Optional): Switch Personas to Prove It's Not a Script

Run this only if time allows — the core sale is already done in Exercise 1. But it's the fastest way to kill the "is this just a canned demo?" doubt. Different employees get different, correct answers because the agent applies real policy and per-employee data.

. Send an email containing `reset`, then run the same short laptop-refresh flow as a different person. Try these:
+
* *alice.johnson@company.com* — EMEA, eligible. The baseline you already ran.
* *maria.garcia@company.com* — LATAM. She sees a *different regional catalog* — the options that are valid where she is.
* *john.doe@company.com* — EMEA, same catalog as Alice, but a *different laptop on file*. Same region, different personal data.

. Narrate the point as you switch: "Same question, different employee. Maria sees her region's catalog. John's in Alice's region but he's on a different machine, so his eligibility reads differently. The agent is applying policy and reading each person's real data — this isn't a fixed script with the names swapped."

=== Verify

Two or three personas each produced a correct, region-appropriate response, and at least one differed from Alice's. That contrast is the proof that the agent is reasoning over policy and data, not replaying a recording.

== Positioning: What You're Actually Selling

Your job here isn't to click through a form. It's narration and framing. Keep coming back to the business outcomes the customer's leadership cares about:

* *Faster resolution* — the request is captured correct and complete in one conversation, so tickets close faster and throughput goes up.
* *Higher compliance* — policy and eligibility are applied automatically, every time, so requests follow the standard instead of relying on the employee to know it.
* *Fewer rejected requests* — no missing or incorrect information means fewer bounce-backs and re-work for IT.

Expect these questions, and have the answers ready:

* "Is this only for laptops?" — No. The laptop refresh is today's example. The same framework handles other IT processes — Privacy Impact Assessments, RFP generation, access requests, software license requests — by swapping in a specialist agent, its knowledge, and its tools.
* "Does my team have to live in email?" — No. Email is the channel we're showing. Meet users where they are.

== Meet Users Where They Are

This is the line that makes the architecture pay off for the customer. The same agent spans email, Slack, ServiceNow, and a CLI *without losing context*. Adding a channel is adding an adapter — not rewriting the agent. So you start where your people already are today, and you extend to the next channel tomorrow without starting over.

Pair that with the extensibility point and you've described a platform, not a feature: new channel? Add an adapter. New process? Add a specialist agent, its knowledge base, and its MCP connections to the systems of record. The product you demoed for laptop refresh is the same product that handles the next ten IT workflows.
